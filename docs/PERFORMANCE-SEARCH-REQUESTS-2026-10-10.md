# 告警与通知记录搜索请求合并

日期：2026-10-10。前端基线 `3ce4035`；后端当前 `315843f`，本批后端无运行代码改动，独立 Agent 无改动。

## 已确认的问题

- `/alerts` 当前/历史队列：每次输入都修改 URL，并立即触发查询。真实 Chrome + 本地构建 + 模拟 API 复现输入 `payment` 后总请求从初始 1 次增加到 8 次。取消旧请求并不能避免它们已经到达后端。
- `/noticeRecords` 及通知对象的记录抽屉：首次挂载的 resize effect 和 filters effect 都读取记录，浏览器复现首次打开请求 2 次；过滤词每次更新也请求，回车/清空可能再触发额外查询。
- 通知记录缺少读取取消/迟到响应隔离，旧查询可能覆盖当前筛选结果；接口业务失败原先可能被空数组掩盖。

## 已实现

1. 告警和通知记录均在停止输入 300 ms 后提交自动查询，持续输入重新计时。仅延迟输入导致的读取，输入框立即响应；告警 URL 仍立即更新，保持分享视图和返回位置。
2. 回车立即查询并清除待执行计时器；清空查询立即更新且只请求一次。切换队列、其他筛选及分页不等待旧搜索定时器。
3. 输入法组合期间不提交未确认的中间文本；组合完成后查询最终内容，不把选字回车当作第二次搜索。
4. 通知记录由单一 effect 管理首次、筛选和分页读取。增加 AbortSignal、请求序号校验，取消旧请求且忽略迟到结果；主动取消不弹失败提示。
5. 通知记录保留服务端分页和通知对象 UUID 范围；失败显示明确的失败文案，支持原刷新入口重试，不冒充“暂无通知记录”。没有改动通知发送、认领、静默等写操作。

本批未引入新依赖、查询框架或全局数据缓存，也没有更换视觉布局。

## 测量与验证

用 Playwright 的浏览器时钟控制暂停/推进，避免把自动化点击耗时误当作防抖失效；请求本身仍由 Chrome 的网络层发出，API 由测试模拟。

|操作|修改前|修改后|
|---|---:|---:|
|连续输入 payment（不含首次打开）|7 次查询|1 次查询|
|首次打开通知记录|2 次查询|1 次查询|
|等待期间回车提交|可能随后再触发自动读取|立即查询一次，之后无定时器重复读取|

这是上述输入节奏的请求次数，不是生产流量比例或响应时间结论。用户每次输入停顿超过 300 ms 时，仍按停顿次数查询。

- 28 项单元测试，覆盖新增通知记录 signal、对象范围与失败反馈；TypeScript 检查和生产构建通过。
- 新增浏览器用例覆盖当前/历史搜索、299/300 ms 边界、回车、清空、组合输入事件、队列切换、卸载、通知记录翻页/筛选、对象抽屉、迟到结果和错误重试。最初 6 项专项连续三轮通过；补充最终错误展示后再跑最终构建回归。
- 最终构建保持稳定后，全站挂载/关键流程/性能浏览器回归 284 项全部通过。挂载检查不是所有页面所有业务路径的完整验收，模拟组合事件也不等于所有操作系统输入法实测。
